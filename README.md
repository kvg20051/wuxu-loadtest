# WUXU — нагрузочный тест чата с log-файлами

Версия 1.1 · 16 ноября 2026 года. Python 3.11+; HTTPX 0.28.1.

По умолчанию: **30 виртуальных пользователей, окно запуска 300 секунд**, набор за 30 секунд,
паузы 10–30 секунд, streaming, до 3 ходов в диалоге. Включены загрузки настоящих `.log`
по **1 MB**, максимум **30 файлов** за запуск. Модель — `pilot-model`, которая есть в вашем списке.

## Установка и обновление

Распакуйте пакет в `~/_Git_projects/wuxu-loadtest`. При обновлении сохраните свои параметры
из прежнего `run.sh`, затем замените файлы программы. Не удаляйте `.venv`, личный `keys.txt`
и результаты. В новой версии нужен также `log_files.py`. Зависимости не изменились.

```bash
cd "$HOME/_Git_projects/wuxu-loadtest" || exit 1
sudo apt-get update
sudo apt-get install -y python3 python3-venv
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
```

Генератор желательно запускать на отдельной VM. Нужны место под временные файлы и исходящий HTTPS.
TLS проверяется; redirects и неявные HTTP_PROXY/HTTPS_PROXY не используются.

## Сценарий

```text
Генератор → HTTPS/Caddy → Open WebUI → LiteLLM → модель
                              ↓
                    Приём .log, извлечение текста,
                    embeddings / поиск по вложению
```

1. Создать настоящий `.log` заданного размера на диске либо открыть существующий.
2. Передать файл как multipart через `POST /api/v1/files/`, включив обработку.
3. Опросить `GET /api/v1/files/{id}/process/status` до `completed`.
4. Вызвать `POST /api/chat/completions` с `files: [{"type":"file","id":"..."}]`.
5. Получить ответ; следующие ходы сохраняют вложение и историю.
6. После нагрузки удалить обработанные файлы этого запуска, если включена очистка.

Перед нагрузкой выполняются `GET /api/models` для каждого ключа и **один текстовый пробный chat POST**.
Он проверяет модель; upload/RAG проверяются сценариями нагрузки. Ошибка файла не подменяется
обычным текстовым запросом. Модель в Open WebUI должна использовать подключение LiteLLM;
проверяйте фактическое прохождение в LiteLLM Logs/Usage.

Для синтетического файла модель должна вернуть `WUXU_CHECK`, значение которого находится только в логе.
Отсутствие значения в первом ответе считается ошибкой даже при HTTP 200. Это проверяет получение
фрагмента файла, но не прочтение всех строк и не качество анализа. У модели должен работать поиск
по вложениям / Preload Files. Full Context скрипт не включает: файл 300 MB не отправляется целиком в LLM.
Настройки RAG/инструментов модели влияют на результат.

Браузер, вход/2FA, WebSocket, сохранение чатов и отдельный `/api/chat/completed` не эмулируются.
История передаётся в `messages` и хранится только в памяти генератора.

## API-ключ

Нужен **ключ Open WebUI на wuxu.ru**, а не LiteLLM. Он вводится скрыто при запуске.
В скрипт или аргументы команды ключ вписывать не нужно. Пользователю нужны API Keys,
доступ к модели и файлам. Ограничения API endpoints должны пропускать:

- `GET /api/models`;
- `POST /api/chat/completions`;
- `POST /api/v1/files/`;
- `GET /api/v1/files/{id}/process/status`;
- `DELETE /api/v1/files/{id}` — для очистки.

`{id}` — фактический идентификатор, не буквальный текст настройки. Учитывайте способ
сопоставления путей в вашей версии Open WebUI.

Можно сохранить ключ в окружении текущего терминала:

```bash
read -r -s -p 'Ключ Open WebUI: ' WUXU_API_KEY
printf '\n'
export WUXU_API_KEY
```

После работы: `unset WUXU_API_KEY`. **Один ключ = одна учётная запись**, даже при 30 виртуальных
пользователях. Для разных идентичностей создайте `keys.txt` с ключами пользователей по одному
на строке, выполните `chmod 600 keys.txt`, задайте `KEYS_FILE="keys.txt"`.
Ключи дедуплицируются и распределяются циклически. В отчётах — только `key-001`, `key-002` и т. д.
Общий `openwebui-pilot` в LiteLLM может по-прежнему объединять лимиты и расходы.

## Параметры в начале run.sh

```bash
USERS=30
DURATION_SECONDS=300
BASE_URL="https://wuxu.ru"
MODEL="pilot-model"
RAMP_UP_SECONDS=30
THINK_MIN_SECONDS=10
THINK_MAX_SECONDS=30
MAX_OUTPUT_TOKENS=512
TOKEN_LIMIT_PARAM="max_completion_tokens"
REQUEST_TIMEOUT_SECONDS=120
MAX_REQUESTS=0
TURNS_PER_CHAT=3
STOP_AFTER_ERRORS=10
STREAM=true
INCLUDE_USAGE=true
KEYS_FILE=""
PROMPTS_FILE=""

UPLOAD_LOGS=true
LOG_FILE_SIZES_MB="1"
LOG_FILES=()
LOG_UPLOAD_EVERY_DIALOGS=1
MAX_UPLOADS=30
UPLOAD_TIMEOUT_SECONDS=300
FILE_PROCESSING_TIMEOUT_SECONDS=600
FILE_POLL_SECONDS=2
CLEANUP_UPLOADED_FILES=true
VERIFY_FILE_CONTENT=true
```

Размеры: **1 MB = 1 000 000 байт**, не MiB; HTTP-заголовки в размер не входят.

```bash
LOG_FILE_SIZES_MB="10"          # Каждый файл — ровно 10 000 000 байт
LOG_FILE_SIZES_MB="1,10,100"    # Чередование между пользователями и диалогами
LOG_FILE_SIZES_MB="300"        # Каждый файл — ровно 300 000 000 байт
```

Дробные размеры допустимы, минимум 256 байт. Перед каждой загрузкой создаётся уникальный файл
с INFO/WARN/ERROR, HTTP 429/503 и DB_POOL_TIMEOUT. Генерация и передача используют ограниченные
буферы, не загружая весь файл в RAM. Локальный временный файл удаляется после попытки загрузки.

Чтобы передавать свои `.log`, задайте Bash-массив:

```bash
LOG_FILES=("/home/kvg/app.log" "/home/kvg/nginx-error.log")
```

Генерация заменяется чтением этих файлов; размеры берутся с диска. Исходники не изменяются
и не удаляются. Не редактируйте их во время теста. Проверка WUXU_CHECK для них не выполняется.
Повторение одинакового файла может использовать серверный кэш; уникальная генерация уменьшает этот эффект.

`LOG_UPLOAD_EVERY_DIALOGS=1` — вложение в каждом диалоге; `3` — в 1-м, 4-м, 7-м и т. д.
Один диалог содержит до `TURNS_PER_CHAT` успешных ответов. Файловые диалоги используют запрос
анализа лога, обычные — встроенные сценарии или JSON-массив из `PROMPTS_FILE`.

`MAX_UPLOADS=30` — общий предел попыток, включая неудачные. После него новые диалоги идут
без файлов; начатые сохраняют вложения. `0` снимает предел. **30 файлов по 300 MB = 9 GB**
исходных данных на сервере до очистки; извлечённый текст и индекс требуют дополнительного места.

`MAX_REQUESTS=0` — по времени. Положительное значение ограничивает число сценариев нагрузки
плюс один предварительный chat POST. Ошибка файла тоже расходует слот, даже без вызова модели.
Upload, polling и DELETE в этот лимит не входят: это верхняя граница chat POST, не всех HTTP-запросов.

## Длительность и очистка

`DURATION_SECONDS` — окно **начала сценариев**, включая ramp-up. Начатый сценарий завершается
целиком: генерация → upload → обработка → ответ. Его обработка и chat POST могут продолжаться
после окна. Поэтому файловый тест может занять существенно больше 5 минут: каждый сетевой этап
имеет свой таймаут; генерация зависит от диска/CPU. Затем выполняется очистка.

Ctrl+C/SIGTERM останавливают новые сценарии, текущие завершаются и формируется отчёт.
Неудачные upload/chat POST автоматически не повторяются. 401/403 и upload 413 прекращают новые
сценарии; действует также `STOP_AFTER_ERRORS`. При 429/503 следующий сценарий пользователя
откладывается минимум на 5 с, с учётом Retry-After.

Очистка удаляет **только ID этого запуска и с ключом загрузившего пользователя**, после всех ответов.
Удаляются файлы со статусами `completed`/`failed`; незавершённая обработка сохраняется.
При таймауте upload файл мог попасть на сервер без возврата ID: статус `unknown_no_id`.
Смотрите ID, имена и результаты очистки в `files.json`. Массовое удаление не используется.
`CLEANUP_UPLOADED_FILES=false` оставляет загруженные файлы на сервере.

## Запуск

```bash
# Без ключа/сети: параметры
bash run.sh --dry-run

# Только список доступных моделей
bash run.sh --list-models

# 2 пользователя, окно 20 с, до 3 сценариев + 1 текстовый пробный POST
bash run.sh --smoke --log-sizes-mb 1

# 30 пользователей, 5 минут, размеры 1/10/100 MB, максимум 30 файлов
bash run.sh --users 30 --duration 300 --log-sizes-mb 1,10,100

# Файлы по 300 MB
bash run.sh --log-sizes-mb 300 --max-uploads 30

# Существующий файл
bash run.sh --log-files /home/kvg/test-300MB.log

# Только создать реальные файлы локально — без ключа и сети
bash run.sh --generate-only --log-sizes-mb 10,100,300

# Текстовый профиль без файлов
bash run.sh --no-upload-logs
```

`--generate-only` создаёт новый подкаталог в `generated-logs/` и выводит полные пути.
Изменить каталог: `--log-dir /home/kvg/testlogs`. Эти файлы не удаляются автоматически.
Для отдельного запуска можно указать `--no-verify-file` или `--no-cleanup-files`.
Аргументы переопределяют переменные. `--smoke` задаёт малый профиль, но **сохраняет выбранные
размеры файлов и таймауты**.

## Результаты и расходы

Каждый запуск создаёт отдельный каталог `results/<UTC-время>-<ID>/`.

| Файл | Содержимое |
|---|---|
| settings.json | Параметры без ключей |
| preflight.json | Отдельный предварительный текстовый запрос |
| requests.csv / requests.jsonl | Сценарии, время этапов, ошибки, токены |
| files.jsonl | Журнал этапов файлов; один upload_id встречается несколько раз |
| files.json / files.csv | Итог по каждому файлу, его ID и очистка |
| summary.json / report.md | Агрегаты и читаемый отчёт |

`requests` — сценарии; `chat_posts` — фактические chat POST нагрузки, без предварительного.
`chat_sent=false` означает отказ до вызова модели.

- `generation_ms`: создание файла;
- `upload_ms`: upload до ответа API;
- `processing_ms`: ожидание обработки, включая polling;
- `elapsed_ms`, `ttft_ms`: отсчёт от chat POST, без предшествующего upload;
- `workflow_ms`: весь сценарий; агрегаты — `workflow_success_ms`;
- `attachment_verified`: true/false либо null, если проверка не выполнялась;
- `accepted_file_bytes`: размеры файлов с полученным ID, без multipart/частичных передач.

Перцентили nearest-rank. Пик параллельности относится к chat POST, не фоновой индексации.
JSON-режим не измеряет TTFT. Настройки сервера могут переопределить streaming/usage.
Ключи маскируются в ошибках, полные ответы и содержимое файлов намеренно в отчёт не записываются.

**Тест расходует реальные токены.** Внешние embeddings могут создавать отдельные расходы.
Usage ответов не гарантирует учёт всех затрат RAG/сервера. Отсутствие usage не означает нулевой расход.
Денежные лимиты задаются в LiteLLM; итог проверяется у шлюза/провайдера. Скрипт стоимость не вычисляет.

Коды выхода: `0` — успешные сценарии без ошибок сценариев/DELETE; `1` — ошибки или нет сценариев;
`2` — настройка/предварительная проверка; `130` — остановка оператором. Намеренное сохранение
файлов само по себе не ошибка. Успех не означает выполнение вашего SLO или корректность всего анализа.

## Диагностика

| Ошибка | Проверить |
|---|---|
| 401/403 | Ключ Open WebUI, API-права, файлы/DELETE, доступ к модели |
| 413 | Лимиты размера в Caddy/Open WebUI; скрипт их не меняет |
| 400 при upload | Разрешено ли расширение .log, текст ошибки |
| file_processing_failed | Извлечение текста, embeddings, хранилище, журнал Open WebUI |
| file_processing_timeout | Очередь, CPU/RAM, объём файлов, processing timeout |
| file_content_not_verified | RAG/Preload Files, поиск по вложению, лимит ответа; модель не вернула метку |
| file_upload_timeout | Канал/таймаут proxy; возможен принятый файл без известного ID |
| cleanup failed | Право DELETE; файл мог остаться, ID есть в files.json |
| 429 | Лимиты пользователя, общего ключа LiteLLM, провайдера |
| 502/503/504 | Caddy/upstream, ресурсы и таймауты |
| empty_response | Лимит reasoning-токенов, отсутствие видимого текста |
| incomplete_stream | Поток оборвался до признака завершения |

Для модели, требующей `max_tokens`, измените `TOKEN_LIMIT_PARAM`. Лимита 512 может быть мало
для reasoning; увеличение меняет профиль/расход. Тест закрытого цикла: при замедлении ответов
пользователи ждут, а поток запросов снижается. Это не измеритель максимального RPS.

```bash
sudo docker stats
sudo docker logs --since 10m --tail 100 ai-pilot-openwebui-1
sudo docker logs --since 10m --tail 100 ai-pilot-litellm-1
```
