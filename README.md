# WUXU — нагрузочный тест Open WebUI → LiteLLM → модель

Версия 1.0 · 16 ноября 2026 года.

Пакет: Python-генератор нагрузки и Bash-обёртка с параметрами в начале файла.
Профиль по умолчанию: **30 виртуальных пользователей, 300 секунд**, набор нагрузки за 30 секунд,
паузы 10–30 секунд после ответов, streaming, до 3 запросов в одном диалоге.
Ключ вводится скрыто при запуске. Боевой тест автоматически не выполняется.

## 1. Что проверяет тест

Путь запроса:

```text
Генератор → https://wuxu.ru → Caddy → Open WebUI → LiteLLM → провайдер модели
```

Используется официальный endpoint Open WebUI `POST /api/chat/completions`.
Перед нагрузкой выполняются `GET /api/models` для каждого ключа и один настоящий пробный POST.
Модель должна быть подключена в Open WebUI именно через LiteLLM: URL клиента сам по себе этого не гарантирует.
Проверить фактическое прохождение запросов можно в LiteLLM Logs/Usage.

Это тест API инференса. Он **не эмулирует** отрисовку браузера, вход и 2FA, загрузку файлов,
RAG, WebSocket-сессии, сохранение чатов в интерфейсе или отдельный вызов `/api/chat/completed`.
История диалога передаётся в `messages` и хранится только в памяти генератора.
Для базового теста выберите обычную модель без подключённых инструментов и Knowledge Base.

**Один ключ = одна учётная запись Open WebUI**, даже при 30 виртуальных пользователях.
Это проверяет параллельные запросы, но лимиты учётной записи остаются общими.
Для 30 реальных идентичностей нужны ключи 30 разных пользователей. Если Open WebUI использует общий
ключ `openwebui-pilot` к LiteLLM, ограничения этого ключа всё равно общие для всех.
Разделение расходов по пользователям зависит от настроенной передачи идентичности из Open WebUI.
Скрипт не подменяет пользовательские заголовки авторизации.

## 2. Установка на Ubuntu

Желательно запускать генератор на другой VM или на рабочем компьютере, чтобы он не отнимал
ресурсы у проверяемого WUXU. Нужны Python 3.11+ и исходящий HTTPS к WUXU.

Скопируйте содержимое архива в каталог `~/wuxu-loadtest`, затем:

```bash
sudo apt-get update
sudo apt-get install -y python3 python3-venv
cd ~/wuxu-loadtest
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
```

Команда `bash run.sh` не требует права executable у файла. TLS проверяется; перенаправления
не выполняются. Неявные `HTTP_PROXY`/`HTTPS_PROXY` из окружения не используются.
Подключения HTTP/1.1 переиспользуются через общий пул, до числа виртуальных пользователей.

## 3. Какой API-ключ нужен

Нужен **ключ Open WebUI на wuxu.ru**, а не виртуальный или master key LiteLLM.

1. Администратор включает API Keys в Settings → Authentication.
2. Для обычного тестового пользователя требуется разрешение API Keys его группы.
3. Пользователь создаёт личный ключ в Settings → Account.
4. Если включены ограничения API endpoints, разрешите **`/api/models` и `/api/chat/completions`**.
5. У пользователя должен быть доступ к выбранной модели.

Пароль и шестизначный код 2FA для этого теста не используются.
Ключ не попадает в параметры командной строки, настройки или отчёт.

При каждом запуске программа запросит ключ скрыто. Чтобы в текущем терминале не вводить его повторно:

```bash
read -r -s -p 'Ключ Open WebUI: ' WUXU_API_KEY
printf '\n'
export WUXU_API_KEY
```

После работы:

```bash
unset WUXU_API_KEY
```

Ключ находится в окружении процесса, поэтому используйте личную тестовую учётную запись.
Запросы обращаются к реальному провайдеру и расходуют его токены. Общий денежный бюджет
задаётся на стороне LiteLLM; клиент не вычисляет и не обещает денежный лимит.

## 4. Параметры в начале run.sh

```bash
USERS=30
DURATION_SECONDS=300
BASE_URL="https://wuxu.ru"
MODEL="gpt-6.1-sol"
RAMP_UP_SECONDS=30
THINK_MIN_SECONDS=10
THINK_MAX_SECONDS=30
MAX_OUTPUT_TOKENS=512
TOKEN_LIMIT_PARAM="max_completion_tokens"
REQUEST_TIMEOUT_SECONDS=120
MAX_REQUESTS=0
TURNS_PER_CHAT=3
STOP_AFTER_ERRORS=10
STREAM=true
INCLUDE_USAGE=true
KEYS_FILE=""
PROMPTS_FILE=""
```

`MODEL` — точный ID, доступный ключу в Open WebUI. Указанный ID — исходное значение для вашей связки;
актуальную доступность программа проверяет перед нагрузкой.

`DURATION_SECONDS` — окно **запуска** запросов, начиная с первого виртуального пользователя,
включая ramp-up. После его окончания новые запросы не запускаются, текущие завершаются либо
достигают полного `REQUEST_TIMEOUT_SECONDS`. Поэтому 300-секундный тест может завершиться
примерно за 420 секунд плюс предварительные проверки.

`MAX_REQUESTS=0` оставляет длительность главным ограничением. При положительном значении
тест может закончиться раньше; лимит включает один пробный POST и все POST нагрузки,
включая неудачные. Минимальное ненулевое значение — 2.

Количество виртуальных пользователей — верхняя граница параллельных запросов. Каждый ждёт свой
ответ и выдерживает паузу; 30 пользователей не означают 30 запросов/с или постоянные 30 запросов
в работе. `RAMP_UP_SECONDS` должно быть меньше `DURATION_SECONDS`.

`max_completion_tokens` подходит для моделей, которым нужен этот параметр. Для модели,
ожидающей `max_tokens`, поменяйте `TOKEN_LIMIT_PARAM`. У reasoning-моделей лимит может включать
скрытые рассуждения: слишком маленький лимит способен дать пустой ответ. Увеличивайте его
по результатам пробного запроса. Повторных платных попыток с другими параметрами скрипт не делает.

Первые запросы выбираются из шести синтетических сценариев: релиз, логи, Python, численные данные,
требования и документы. Последующие уточняют предыдущий ответ. После 3 успешных ходов история сбрасывается.
Ответы в истории ограничены 16 000 символами на ход. Для своих первых запросов укажите
`PROMPTS_FILE="prompts.example.json"` и отредактируйте JSON-массив.

Уникальный идентификатор включается в каждый запрос, уменьшая вероятность полного совпадения
в кэше ответов. Prefix caching модели и другой серверный кэш этим не отключаются.

## 5. Порядок запуска

Проверка параметров без ключа и без сетевых запросов:

```bash
bash run.sh --dry-run
```

Получить доступные модели (только GET, генерации ответа нет):

```bash
bash run.sh --list-models
```

Короткий пробный тест: 2 пользователя, окно 20 секунд, максимум 4 POST вместе с проверочным.
При достижении лимита он закончится раньше:

```bash
bash run.sh --smoke
```

Основной тест с параметрами из начала `run.sh`:

```bash
bash run.sh
```

Аргументы также могут переопределить переменные:

```bash
bash run.sh --users 10 --duration 120 --ramp-up 15
bash run.sh --max-requests 100
```

После проверки ключей и доступности модели выполняется один пробный запрос. Если он неуспешен,
массовая нагрузка не начинается. Пробный POST расходует токены, хранится в `preflight.json` и не
смешивается с метриками нагрузки. Набор нагрузки начинается после его успешного завершения.

`Ctrl+C`/`SIGTERM` прекращают запуск новых запросов. Текущие запросы завершаются в пределах таймаута,
после чего сохраняется отчёт. Принудительное уничтожение процесса может оставить только CSV/JSONL.

Автоматических повторов неудачного POST **нет**. Для HTTP 429/503 следующий запрос того же пользователя
откладывается не меньше `Retry-After`; без корректного заголовка — не меньше 5 секунд.
401/403 останавливают запуск новых запросов. По умолчанию 10 последовательных ошибок в порядке
завершения запросов также останавливают тест. Уже выполняющиеся запросы завершаются.
Ошибки HTTP 200 с полем `error` внутри SSE тоже считаются ошибками.

Коды выхода: `0` — есть успешные запросы и нет ошибок; `1` — ошибки/нет запросов нагрузки;
`2` — ошибка настройки или предварительной проверки; `130` — остановка оператором.
Код `0` не означает выполнение какого-либо SLO: сравните p95 с вашим требованием отдельно.

## 6. Тест разных пользователей

```bash
cp keys.example.txt keys.txt
chmod 600 keys.txt
nano keys.txt
```

Вставьте ключи разных пользователей по одному на строку, без кавычек. В начале `run.sh`:

```bash
KEYS_FILE="keys.txt"
USERS=30
```

Либо:

```bash
bash run.sh --keys-file keys.txt
```

Ключи дедуплицируются и распределяются по виртуальным пользователям циклически.
Если ключей больше пользователей, лишние проходят проверку моделей, но в нагрузке не используются.
В отчёте остаются только номера `key-001`, `key-002` и т. д.

## 7. Результаты

Каждый запуск создаёт новый каталог `results/<UTC-время>-<случайный ID>/`:

| Файл | Содержимое |
|---|---|
| `settings.json` | Параметры запуска без ключей |
| `preflight.json` | Отдельный результат пробного POST |
| `requests.csv` | Метрики каждого запроса; удобно открыть в Excel |
| `requests.jsonl` | Те же записи для программного анализа |
| `summary.json` | Агрегаты, распределение статусов и результаты по виртуальным пользователям |
| `report.md` | Читаемое резюме |

В отчёте есть полная задержка ответа p50/p95/p99, задержка первого **видимого текста** TTFT,
число запросов, ошибки, фактическая пиковая параллельность и сообщённые сервером токены.
`headers_ms` — время до HTTP-заголовков, оно не подменяет TTFT. В режиме без streaming TTFT не измеряется.
Промпты, полные ответы, ключи, пароли и токены сессий не сохраняются; сохраняется ограниченный текст ошибок
с маскированием ключей. Серверные журналы Open WebUI/LiteLLM ведутся согласно их собственным настройкам.

Перцентили рассчитываются методом nearest-rank. `latency_success_ms` и `ttft_success_ms` включают
успешные запросы; `latency_all_ms` включает также ошибки. Текстовый ответ, обрезанный лимитом токенов,
может быть успешным технически; число `finish_reason=length` показывается отдельно.

**Нет usage ≠ нет расходов.** Скрипт показывает количество запросов с доступной статистикой,
а суммы токенов охватывают только известные данные. Если сервер выполняет дополнительные вызовы
моделей или ретраи, они могут не полностью отражаться в возвращённом usage. Пробный POST учитывайте
отдельно. Итоговые расходы и лимиты проверяйте в LiteLLM и кабинете провайдера.

При 30 пользовательских ключах общий `openwebui-pilot` в LiteLLM всё равно может объединять расходы.
Для чистого измерения можно выделить тесту отдельное подключение/ключ шлюза, но это не требуется для запуска.

## 8. Как читать ошибки

| Результат | Что проверить |
|---|---|
| 401 | Ключ именно Open WebUI, включены API Keys, ключ не отозван |
| 403 | Разрешённые endpoints, права пользователя, доступ к модели |
| Модели нет в `/api/models` | Точный ID и разрешения модели в Open WebUI |
| 400 | Текст ошибки: параметры, имя модели, контекст, лимит токенов |
| 429 | Лимиты пользователя/Open WebUI/общего ключа LiteLLM/провайдера |
| 502/503/504 | Caddy, Open WebUI, LiteLLM, доступность и таймауты upstream |
| `provider_error` при HTTP 200 | Ошибка передана внутри SSE; смотрите текст и LiteLLM Logs |
| `incomplete_stream` | Поток оборвался до `[DONE]` и `finish_reason` |
| `empty_response` | Лимит reasoning-токенов, инструменты или модель не дала видимого текста |
| `protocol_error` | Endpoint вернул HTML, фоновый task ID или другой несовместимый ответ |
| Ошибка `stream_options` | Установите `INCLUDE_USAGE=false`; статистика токенов может отсутствовать |

Рост TTFT может быть связан с очередью провайдера или лимитами ключа, а не только ресурсами VM.
Тест закрытого цикла (closed-loop): замедлившийся ответ уменьшает частоту новых запросов.
Это модель поведения пользователей, а не измеритель максимального устойчивого RPS.
Малое количество запросов делает p99 близким к максимуму и статистически неустойчивым.

Во втором терминале на сервере WUXU полезно наблюдать:

```bash
sudo docker stats
```

После теста:

```bash
sudo docker logs --since 10m --tail 100 ai-pilot-openwebui-1
sudo docker logs --since 10m --tail 100 ai-pilot-litellm-1
```

## 9. Запуск без Bash и локальные тесты

```bash
.venv/bin/python wuxu_loadtest.py --users 30 --duration 300
.venv/bin/python -m unittest discover -s tests -v
```

На Windows используйте Python 3.11+, `python -m venv .venv`, затем `.venv\Scripts\python.exe`.
Оффлайн-тесты используют искусственные ответы HTTPX, не обращаются к WUXU и не расходуют токены.
